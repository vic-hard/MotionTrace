# MotionTrace — план технического прототипа

## Цель

Проверить, можно ли на Android надёжно записывать датчик **Gravity** с выключенным экраном с тем же качеством, что у [Sensor Logger](https://play.google.com/store/apps/details?id=com.kelvin.sensorapp): реальная частота, пропуски, временные метки, поведение на разных телефонах. Результат — отчёт со сравнением, по нему заказчик решает, продолжать ли полную разработку.

**Входит:** Android, один датчик (Gravity), запись в фоне, минимальный интерфейс, скрипт анализа, сравнение с Sensor Logger на двух телефонах.

**Не входит:** iOS, другие датчики, микрофон, графики, полноценный интерфейс.

## Принятые решения

- **Стек:** React Native + Expo (SDK 57, RN 0.86) с локальным нативным модулем `modules/sensor-recorder` (Kotlin; заготовка Swift на будущее). Прототип сразу делается в структуре будущего приложения, чтобы код не выбрасывать.
- **Запись идёт только в нативном слое.** JS отправляет команды (старт / стоп / статус) и получает события статуса. Сырой поток данных в JS не передаётся.
- **Классы записи не зависят от Expo** (`SensorRecorder.kt`, `CsvWriter.kt`, `RecorderService.kt`). `SensorRecorderModule.kt` — тонкая обёртка. Если заказчик выберет полностью нативные приложения, классы переносятся без изменений.
- **Датчики — только через SDK платформы** (`SensorManager`), без сторонних библиотек.
- **Тип foreground service — `health`.** Технически ему достаточно объявленного `HIGH_SAMPLING_RATE_SENSORS`. До публикации в Google Play нужно решить: `health` или `specialUse` (зависит от позиционирования приложения).
- Пакет приложения: `com.limedevelopment.motiontrace`. Навигация: Expo Router (`src/app/`).
- Из функционала заказчика убраны компас и графики. Спектральный анализ в скрипт не входит (заказчик решил не брать).

## Что сделано в этапе 3

Код — в `modules/sensor-recorder/android/src/main/java/com/limedevelopment/motiontrace/sensorrecorder/`, по одному классу на файл. От Expo зависят только `SensorRecorderModule.kt` и `SensorRecorderExceptions.kt`, остальное переносится в нативное приложение без изменений.

- `SensorRecorder.kt`: подписка на `Sensor.TYPE_GRAVITY` на собственном `HandlerThread` (приоритет `URGENT_DISPLAY`); `Handler` этого потока передаётся в `registerListener`, поэтому `onSensorChanged` вызывается на нём.
  - `start()` состоит из шагов `findSensor` → `openFiles` → `startThread` → `subscribe` → `scheduleTicks`; при ошибке `abortStart` откатывает сделанное. `subscribe` — последний шаг, который может упасть: после него события уже пишутся в CSV, и откат с чужого потока недопустим.
  - Один объект = одна запись (`start()` → `stop()`). Приём событий, запись CSV и тик раз в секунду (flush + статус) идут в одной очереди одного потока, поэтому блокировок на запись нет.
  - `stop()` отписывается от датчика, дописывает уже пришедшие события, закрывает файлы и ждёт этого не дольше 2 с.
  - Ошибка записи на диск останавливает запись; текст ошибки попадает в статус и метаданные.
- `RecordingMode.kt`: режим `100hz` — период 10 000 мкс; `max` — `SENSOR_DELAY_FASTEST` (выше 200 Гц возможно благодаря `HIGH_SAMPLING_RATE_SENSORS`). `maxReportLatencyUs = 0` (без пакетной доставки).
- `SampleStats.kt`: счётчики по записанным строкам (число, первая/последняя метка, максимальный интервал, средняя частота). Неизменяемый снапшот в `@Volatile`-поле: пишет только поток рекордера, читатели всегда видят согласованные значения. Поля жизненного цикла (`state`, `error`, время старта/стопа) пишут два потока, поэтому они отдельно, переходы — через `@Synchronized`.
- `RecorderStatus.kt`: статус для UI и метаданных. `ClockPair.kt`: пара часов `elapsedRealtimeNanos` ↔ `currentTimeMillis` (чтение UTC между двумя чтениями монотонных часов, берётся середина) и смещение для пересчёта в UTC.
- `CsvWriter.kt`: `BufferedWriter` с буфером 64 КБ, flush раз в секунду (данные переживают падение приложения), `fsync` при закрытии.
- `MetadataWriter.kt`: JSON на старте (`writeStart`) и с результатами на стопе (`writeStop`), через временный файл и переименование.
- **Файлы:** `<external files dir>/recordings/gravity_<yyyy-MM-dd_HH-mm-ss>_<режим>.csv` и `.json` с тем же именем. Папка приложения, разрешения не нужны, забрать файлы: `adb pull /sdcard/Android/data/com.limedevelopment.motiontrace/files/recordings`.
- **Формат CSV:**
  ```
  sensor_timestamp_ns,time_utc_ns,seconds_elapsed,x,y,z
  ```
  - `sensor_timestamp_ns` — исходный `SensorEvent.timestamp` (монотонное время от включения, `elapsedRealtimeNanos`), **хранится всегда без пересчёта**;
  - `time_utc_ns` — `sensor_timestamp_ns` + смещение, зафиксированное на старте записи;
  - `seconds_elapsed` — от первого измерения записи, десятичная дробь с 9 знаками (точно, без экспоненты);
  - `x,y,z` — `float` в кратчайшей точной записи (`Float.toString`, возможна экспонента вида `1.2E-4`).
- **Метаданные (JSON рядом с CSV)** пишутся на старте и перезаписываются на стопе (через временный файл и переименование):
  - `device`: производитель, бренд, модель, версия Android и SDK;
  - `sensor`: `name`, `vendor`, `version`, `minDelayUs`, `maxDelayUs`, `fifoMaxEventCount`, `fifoReservedEventCount`, `resolution`, `maximumRange`, `powerMa`, `isWakeUpSensor`;
  - `recording`: режим, запрошенный период, `maxReportLatencyUs`;
  - `clockAtStart` / `clockAtStop`: пара `elapsedRealtimeNanos` ↔ `currentTimeMillis` и смещение (по паре на стопе видно расхождение часов за запись);
  - `result` (только после стопа): число измерений, первая/последняя метка, длительность, средняя частота, максимальный интервал, число разрывов `gapCount` (с этапа 4), ошибка. **Нет `result` — запись оборвалась.**
- Команды модуля (`SensorRecorderModule.kt`, тонкая обёртка):
  - `start(mode: '100hz' | 'max')` / `stop()` — `AsyncFunction`, возвращают статус (после `await stop()` файлы уже закрыты);
  - `getStatus()` — `Function`: `isRecording`, `mode`, `csvPath`, `durationSec`, `sampleCount`, `rateHz` (средняя по меткам датчика), `maxIntervalMs`, `gapCount` (с этапа 4), `error`;
  - событие `onStatus` — на старте, раз в секунду и после остановки;
  - ошибки команд: `ERR_INVALID_MODE`, `ERR_ALREADY_RECORDING` (`SensorRecorderExceptions.kt`);
  - рекордер запоминается до `start()`: `stop()` достанет его при любом исходе старта, а ошибка неудачного старта видна в `getStatus()`;
  - при перезагрузке JS (`OnDestroy`) запись останавливается и закрывается корректно; новый экземпляр модуля о ней не знает и показывает пустой статус. *С этапа 4 иначе: запись живёт в сервисе и переживает перезагрузку JS.*
- iOS: заглушка с тем же API (`start` выдаёт ошибку `ERR_NOT_SUPPORTED`).
- JS: публичный вход модуля — `modules/sensor-recorder/index.ts`, импорт через алиас `@modules/sensor-recorder`. Экран — `src/features/recorder/screens/RecorderScreen.tsx` (временные кнопки «Start 100 Hz / Start max / Stop» и статус; полноценный экран — этап 5), состояние — в `useRecorderScreen.ts`, маршрут `src/app/index.tsx` только реэкспортирует экран.
- В M1 рекордер управляется модулем напрямую. На этапе 4 управление переехало в foreground service.
- Линтер: ESLint (`eslint-config-expo`) + Prettier; `npm run lint` проверяет `src` и `modules`. `.gitattributes` фиксирует LF, иначе Prettier ругается на CRLF под Windows.
- Проверено: `tsc`, `npm run lint`, сборка и запись на Samsung Galaxy A52 (SM-A525F, Android 14, датчик `gravity Non-wakeup` от Qualcomm), экран включён:
  - `100hz`: фактически **105,03 Гц** (интервал 9,521 мс), `max`: **210,06 Гц** (4,761 мс), хотя `minDelay` = 5000 мкс. Датчиковый процессор работает на фиксированных частотах и берёт ближайшую не ниже запрошенной — учесть при сравнении с Sensor Logger;
  - разброс интервалов ~0,05 мкс: метки ставит датчиковый процессор, а не момент доставки, поэтому пропуск виден как выпавшее измерение, а не как неровный интервал;
  - пропусков и немонотонных меток нет; `time_utc_ns` и `seconds_elapsed` сходятся с меткой; первое измерение через ~60 мс после старта, последнее — за 9–18 мс до стопа;
  - экран после Stop совпадает с `result` в JSON;
  - после `am force-stop` CSV обрывается на целой строке, данные есть до последнего ежесекундного flush (потеря < 1 с), в JSON нет `result`;
  - после перезагрузки JS во время записи у записи есть `result` без ошибки.
  - Повторный прогон после рефакторинга по код-ревью (7 октября): все пункты выше подтвердились, формат JSON не изменился.

## Что сделано в этапе 4

- `RecorderService.kt` (без Expo): foreground service типа `health`, объявлен в манифесте модуля (`exported="false"`). Работает ровно столько, сколько идёт запись:
  - `RecorderService.start(context, mode)` создаёт и запускает `SensorRecorder` синхронно (ошибка старта сразу уходит в JS), затем вызывает `startForegroundService`. Сервис в `onStartCommand` всегда вызывает `startForeground` (это обязательно после `startForegroundService`, даже если запись уже остановили), затем останавливается сам, если записи нет;
  - как бы ни закончилась запись (команда Stop, кнопка в уведомлении, ошибка записи на диск), по последнему статусу сервис останавливает себя на главном потоке; уведомление и WakeLock уходят вместе с ним;
  - если система остановит сервис раньше записи, `onDestroy` закрывает файлы с ошибкой «The foreground service was stopped»; если `startForeground` отказал — запись останавливается с текстом ошибки (`SensorRecorder.stop(error)`);
  - `START_NOT_STICKY`: после убийства процесса продолжать нечего — CSV обрывается на последнем ежесекундном flush, в JSON нет `result`.
- `PARTIAL_WAKE_LOCK` на всё время жизни сервиса: Gravity — не wake-up датчик, при спящем процессоре FIFO переполняется и события теряются. В Doze WakeLock процесса с foreground service система не отключает.
- Уведомление (канал «Recording», `IMPORTANCE_LOW`, без звука): «Recording gravity», режим, секундомер от старта, кнопка **Stop**; нажатие открывает приложение. Иконка — `res/drawable/sensor_recorder_notification.xml` модуля.
- Запись теперь принадлежит процессу, а не экземпляру модуля: модуль подписывается на статус (`addStatusListener` в `OnCreate`, отписка в `OnDestroy`), запись переживает перезагрузку JS и смахивание приложения из недавних.
- `gapCount` в `SampleStats` → `RecorderStatus` → `result` JSON и экран («Gaps»): число интервалов больше 2× от среднего интервала до них. Android не сообщает о потерянных событиях, пропуск виден только по меткам (они на ровной сетке, выпавшее измерение даёт двойной интервал). Точный разбор — в скрипте анализа.
- JS: перед стартом запрашивается `POST_NOTIFICATIONS` (Android 13+, `PermissionsAndroid`, `lib/notificationPermission.ts`); отказ не мешает записи — уведомление просто не видно в шторке. `expo-keep-awake` удалён: экран во время записи гаснет как обычно.
- Проверено: `tsc`, `npm run lint`, сборка release APK; в итоговом манифесте есть сервис с типом `health` и все разрешения (targetSdk 36).
- Проверено на Galaxy A52 (SM-A525F, Android 14), 11 октября:
  - во время записи сервис в foreground с типом `health` (`dumpsys activity services`: `isForeground=true`, тип `0x100`), держится `PARTIAL_WAKE_LOCK 'MotionTrace:SensorRecorder'`; после Stop сервис и WakeLock освобождены (в `dumpsys power` пара ACQ/REL в журнале, в секции `Wake Locks:` блокировки нет). Активные блокировки смотреть так: `adb shell "dumpsys power | grep -A10 '^Wake Locks:'"` — простой `grep` цепляет и журнал;
  - в dev-сборке экран не гаснет сам: Expo в режиме разработки включает keep-awake (`expo/src/launch/withDevTools.tsx`), WindowManager держит `SCREEN_BRIGHT_WAKE_LOCK` от имени приложения. Тесты с выключенным экраном и Doze — только на release APK;
  - `am force-stop` во время записи (`max`): CSV обрывается на целой строке, в JSON нет `result`, данные до обрыва без пропусков;
  - **основной тест — 60 минут, release APK, без кабеля, экран выключен, настройки батареи Samsung по умолчанию:**

    | | `100hz` | `max` |
    |---|---|---|
    | Длительность | 3622,6 с | 3678,4 с |
    | Измерений | 380 483 | 772 743 |
    | Средняя частота | 105,033 Гц | 210,079 Гц |
    | Разрывы (`gapCount` и проверка CSV) | 0 | 0 |
    | Максимальный интервал | 9,584 мс (+0,7 % к медиане) | 4,764 мс (+0,07 %) |
    | Ст. отклонение интервала | 0,59 мкс | 0,09 мкс |
    | Дрейф частоты за час | +0,02 % (105,017 → 105,038 Гц) | +0,006 % (210,071 → 210,083 Гц) |
    | Размер CSV | 31 МБ | 63 МБ |

    Немонотонных меток и битых строк нет, `result` без ошибки, частоты те же, что при включённом экране.
  - Частота опроса медленно плывёт (вероятно, температурный уход генератора датчика — не проверялось), метки при этом точные. Отдельные скачки меток на ±47–63 мкс (100 Гц) и ±1–4 мкс примерно раз в минуту (`max`) идут парами и взаимно гасятся — похоже на подстройку часов датчикового процессора, это не пропуски.
  - Системное время относительно монотонных часов уходит за час на 0,06–0,21 мс (`clockAtStart` / `clockAtStop`), на столько же к концу записи может ошибаться `time_utc_ns`.
- Не проверено (досмотреть на этапе 7): кнопка Stop в уведомлении, смахивание приложения из недавних и перезагрузка JS во время записи, принудительный Doze (`dumpsys deviceidle force-idle`), отказ в разрешении на уведомления, ветка без типа сервиса на Android 10–13.

### Этап 6. Скрипт анализа (Python)

- Чтение CSV MotionTrace и Sensor Logger.
- Метрики:
  - фактическая частота, разброс интервалов;
  - пропуски — интервалы больше 2× номинального; номинал брать как скользящую медиану: частота за час плывёт на сотые доли процента (см. этап 4);
  - число измерений относительно ожидаемого — по средней частоте, а не по медиане всей записи, иначе дрейф выглядит как «потерянные» измерения.
- Выравнивание сигналов по времени: общая сетка и сдвиг по максимуму взаимной корреляции. После выравнивания — корреляция Пирсона и RMSE по каждой оси.
- Графики и сводная таблица.

### Этапы 7–8. Отладка и тестирование

- **Сценарии:** «на столе», «дыхание», «движение», длительная запись 30–60 минут с выключенным экраном, оба режима, 2 телефона разных производителей.
- **Частоту и пропуски меряем, запуская приложения по очереди:** Android настраивает датчик на максимальную частоту среди всех подписчиков. Значения (дыхание, движение) сравниваем при одновременной записи с одинаковой частотой.

## Правила проекта

- Зависимости ставить только через `npx expo install` (подбирает версии под SDK), не `npm install <pkg>`.
- `android/` и `ios/` генерируются (`npx expo prebuild`), руками не правятся и не коммитятся. Нативные настройки — в `app.json`, config plugins и манифесте модуля.
- В `AsyncFunction` не выполнять долгую работу: все `AsyncFunction` всех Expo-модулей делят один фоновый поток.
- Kotlin-код удобнее редактировать и отлаживать, открыв `android/` в Android Studio.

## Открытые вопросы (после прототипа)

- Тип foreground service для Google Play: `health` или `specialUse`.
- Фоновая запись на iOS без микрофона и GPS (ограничение iOS, решение за заказчиком). Если iOS будет: отправку записей повторить нативно через `UIActivityViewController` (принимает несколько файлов сразу, ~30 строк Swift).
- Формат звука для будущего микрофона: WAV или ещё и AAC.
- Переход на Expo SDK 58 (RN 0.88) после его стабильного релиза.
